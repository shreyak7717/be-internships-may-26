# Scale Plan — Signals Service @ 10k RPS

## Data Model / Indexes

SQLite is replaced by **PostgreSQL** (Aurora Serverless v2 or RDS Multi-AZ) for
production horizontal scale.

```sql
-- Covering index for the per-user listing query (GET /v1/signals)
CREATE INDEX CONCURRENTLY idx_signals_user_created
    ON signals (user_id, created_at DESC);

-- Unique index enforces atomic idempotency at the DB layer
CREATE UNIQUE INDEX CONCURRENTLY idx_signals_idem_key
    ON signals (idempotency_key)
    WHERE idempotency_key IS NOT NULL;
```

`BRIN` indexes can replace `B-tree` on `created_at` once data grows beyond
~50 M rows (monotonically increasing timestamps are ideal for BRIN).

## Idempotency Across Instances

Every instance shares one PostgreSQL primary.  
The insert is:

```sql
INSERT INTO signals (..., idempotency_key, ...)
VALUES (...)
ON CONFLICT (idempotency_key) DO NOTHING
RETURNING *;
```

- If the row already exists the `RETURNING` clause returns 0 rows.
- The app then re-`SELECT`s by `idempotency_key` to get the existing row.
- No race window: the `UNIQUE` constraint + `ON CONFLICT` is fully atomic.

For *ultra-hot* idempotency keys (rare retries), an optional **Redis** layer
(Elasticache cluster, 1 primary + 1 replica per AZ) caches responses for 24 h:

```
GET  idem:{key}  → hit → return cached JSON immediately
MISS             → proceed to Postgres INSERT
SET  idem:{key}  EX 86400  (after successful write)
```

This reduces read load on Postgres without any correctness trade-off because
the DB unique constraint is still the source of truth.

## Rate Limiting Across Instances

**Current (single-instance):** in-memory sliding-window array — correct inside
one process, invisible to other instances.

**Production path (no Redis):**  
Use PostgreSQL itself via a small advisory-lock + counter table:

```sql
CREATE TABLE rate_counters (
  user_id   TEXT,
  window    BIGINT,          -- UNIX minute: floor(epoch / 60)
  cnt       INT DEFAULT 0,
  PRIMARY KEY (user_id, window)
);

INSERT INTO rate_counters (user_id, window, cnt) VALUES ($1, $2, 1)
ON CONFLICT (user_id, window) DO UPDATE
  SET cnt = rate_counters.cnt + 1
RETURNING cnt;
```

The returned `cnt` tells us whether the request is within the limit.  
Old rows are deleted by a background job or TTL-aware cleanup query.

**With Redis (preferred at high RPS):**  
Sliding-window Lua script — atomic, sub-millisecond:

```lua
local key   = KEYS[1]
local now   = tonumber(ARGV[1])
local limit = tonumber(ARGV[2])
local win   = tonumber(ARGV[3])   -- 60000 ms

redis.call('ZREMRANGEBYSCORE', key, 0, now - win)
local cnt = redis.call('ZCARD', key)
if cnt < limit then
  redis.call('ZADD', key, now, now .. math.random())
  redis.call('PEXPIRE', key, win)
  return 1   -- allowed
end
return 0     -- blocked
```

## Observability (Logs / Metrics / Alerts)

| Layer       | Tool                           | What we capture                          |
|-------------|--------------------------------|------------------------------------------|
| Structured logs | Fastify + Pino → Loki / CloudWatch | request id, userId, latency, status  |
| Metrics     | `prom-client` → Prometheus / Grafana | p50/p95/p99 latency, 4xx/5xx rate, DB pool wait |
| Tracing     | OpenTelemetry → Jaeger / Tempo | DB query spans, downstream calls         |
| Alerting    | Grafana Alertmanager           | error rate > 1 %, p99 > 500 ms, pool exhaustion |

Each request carries an `X-Request-Id` header (generated by Fastify's
`requestIdHeader` option) that propagates through all log entries.

## Failure Modes

| Failure                   | Behaviour                                                              |
|---------------------------|------------------------------------------------------------------------|
| DB transient error        | Retry with exponential back-off + jitter (up to 5 attempts, max 1 s)  |
| DB primary down           | PgBouncer pauses connections; ALB health checks drain the pod          |
| DB replica lag            | Reads fall back to primary (read-after-write consistency guaranteed)   |
| Partial outage (1 AZ)     | Multi-AZ RDS promotes replica in < 60 s; Kubernetes re-schedules pods  |
| Idempotency store miss    | Falls through to Postgres — no correctness loss, slightly higher DB load |
| Rate-limit store miss     | Falls back to in-process counter — per-instance quota, documented trade-off |

```
                                │
                   ┌────────────▼────────────┐
                   │  AWS ALB  (multi-AZ)    │  ← TLS termination
                   └──┬──────────┬───────────┘
                      │          │
           ┌──────────▼──┐  ┌───▼──────────┐
           │ Fastify Pod │  │ Fastify Pod  │  × N  (EKS HPA, ~20 pods)
           │  Node 20    │  │  Node 20     │  each ~500 RPS @ 4 vCPU
           └──────┬──────┘  └──────┬───────┘
                  │                │
        ┌─────────▼────────────────▼──────────┐
        │          PgBouncer  (pool_mode=transaction, pool_size=20) │
        └─────────────────────┬───────────────┘
                              │
               ┌──────────────▼───────────────┐
               │   Aurora PostgreSQL Primary   │  ← writes + idem inserts
               └──────────────┬───────────────┘
                              │ streaming replication
               ┌──────────────▼───────────────┐
               │   Aurora PostgreSQL Replica   │  ← reads (GET /signals)
               └──────────────────────────────┘

        ┌─────────────────────────────────────┐
        │ Elasticache Redis  (cluster mode)   │  ← rate-limit counters
        │  3 shards × 2 replicas              │     + idem response cache
        └─────────────────────────────────────┘
```
